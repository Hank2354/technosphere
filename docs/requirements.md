# Основные требования к сервису ТехноСфера

## Назначение

Сервис сопровождает заявку на оформление документов на продукцию от обращения клиента до доставки результата. Каждый участник видит доступные ему заявки и выполняет действия в рамках своей роли.

Это исходная версия требований. Технологический стек, точные поля форм и окончательная модель данных будут определены при проектировании.

## Роли и права

В системе две основные роли: пользователь и сотрудник. У сотрудника есть тип: менеджер, специалист или доставка.

Клиент регистрируется самостоятельно. Учётные записи сотрудников создаются отдельно; публичная регистрация не должна позволять получить права сотрудника. Конкретный способ создания сотрудников будет выбран при реализации.

| Участник | Доступ и действия |
|---|---|
| Клиент | Свои заявки, создание и отправка заявки, ответы на уточнения, согласование стоимости, счёт, подтверждение оплаты, отслеживание статуса |
| Менеджер | Входящие заявки, проверка полноты данных, запрос уточнений, передача на анализ, определение стоимости, выставление счёта, подтверждение оплаты |
| Специалист | Доступные для анализа и оформления заявки, принятие в работу, заключение о необходимых документах, загрузка готовых документов |
| Доставка | Готовые к отправке заявки, сведения для доставки, способ отправки, трек-номер, отметка о доставке |

Ограничения доступа проверяются сервером для заявок, комментариев и файлов.

## Данные заявки

Основные сведения, определённые на этапе обсуждения:

- Название и описание продукции.
- Код ТН ВЭД.
- Сведения о заявителе и контакты для связи.
- Производитель и страна производства.
- Приложенные документы и материалы.
- Сведения для доставки готовых документов.

В процессе обработки к заявке добавляются:

- Ответственный менеджер и специалист.
- Заключение специалиста и перечень необходимых документов.
- Предложенная стоимость и решение клиента по её согласованию.
- Счёт и сведения о подтверждении оплаты.
- Готовые документы.
- Способ доставки, трек-номер и результат доставки.
- Комментарии и история изменения статусов.

Обязательность отдельных полей и формат кода ТН ВЭД будут уточнены при проектировании формы заявки. Количество позиций продукции в одной заявке также пока не определено.

## Основной процесс

| Этап | Ответственный | Результат |
|---|---|---|
| Подача заявки | Клиент | Заявка отправлена менеджеру |
| Первичная проверка | Менеджер | Данные готовы для анализа либо клиенту направлен запрос уточнений |
| Уточнение | Клиент | Недостающие сведения добавлены и возвращены менеджеру |
| Анализ | Специалист | Подготовлены заключение и перечень необходимых документов |
| Расчёт стоимости | Менеджер | Клиенту направлена стоимость на согласование |
| Согласование | Клиент | Стоимость принята либо отклонена |
| Выставление счёта | Менеджер | Клиент получил счёт |
| Подтверждение оплаты | Менеджер | Зафиксировано поступление оплаты, заявка доступна для оформления |
| Оформление | Специалист | Готовые документы загружены и переданы в отдел доставки |
| Отправка и доставка | Сотрудник доставки | Зафиксированы отправка и завершение доставки |

Назначение и точные названия статусов, допустимые переходы, повторное согласование стоимости, отмена заявки и отказ в оформлении будут описаны отдельно до реализации процесса.

## Упрощения первой версии

Для учебной реализации предлагаются следующие решения:

- Переписка по уточнениям ведётся в комментариях к заявке.
- Менеджер прикрепляет счёт в виде файла.
- Клиент может прикрепить подтверждение оплаты; факт оплаты подтверждает менеджер после проверки.
- Специалист прикрепляет готовые документы в виде файлов.
- Сотрудник доставки вручную указывает способ отправки, трек-номер и результат доставки.
- Действия фиксируются в истории заявки с указанием автора и времени.

Такая первая версия позволяет продемонстрировать весь процесс без интеграции с банком, службой доставки или сервисом автоматического оформления документов.

## Основные правила

1. Клиент имеет доступ только к своим заявкам.
2. Анализ начинается после проверки исходных данных менеджером.
3. Стоимость определяет менеджер после получения заключения специалиста.
4. Счёт выставляется после согласования стоимости клиентом.
5. Подтверждение, загруженное клиентом, само по себе не переводит заявку в оплаченное состояние.
6. Оформление документов начинается после подтверждения оплаты менеджером.
7. Заявка передаётся в доставку после загрузки готовых документов специалистом.
8. Каждый переход статуса должен соответствовать текущему этапу и правам сотрудника.

## Предварительный состав страниц

- Регистрация и вход.
- Личный кабинет клиента со списком заявок.
- Создание и редактирование заявки.
- Карточка заявки с данными, комментариями, файлами и историей.
- Панель менеджера.
- Панель специалиста с очередями анализа и оформления.
- Панель доставки.

Одна карточка заявки может использоваться всеми участниками; доступные сведения и действия зависят от роли и этапа обработки.

## Требования практикума

- Архитектура MVC и модульная структура.
- Разделение представления, бизнес-логики и доступа к данным.
- База данных и паттерн Repository; контроллеры не обращаются к БД напрямую.
- Асинхронные операции с БД и сетевыми запросами.
- Обмен данными между клиентской и серверной частями в JSON.
- Автоматизированные тесты ключевых бизнес-правил в отдельном проекте или модуле.
- Валидация входных данных, защита от SQL-инъекций, аутентификация и авторизация.
- Секреты хранятся вне исходного кода.
- GitHub, осмысленные коммиты, ветки и фиксация реального вклада участников.
- Отчёт Word на 30–40 страниц без приложений и листинга кода, с диаграммами, скриншотами и результатами проверок.

## Организация разработки

Для отдельных задач используются GitHub Issues, рабочие ветки и pull request в основную ветку main. Реальные участники и их вклад отражаются в истории разработки и отчёте.

В задании требуется команда из 2–4 человек. Сейчас планируется индивидуальное выполнение; разрешение преподавателя пока не получено. Использование веток и pull request одним автором не заменяет согласование индивидуального формата.

## Ближайшие шаги

1. Создать репозиторий GitHub и сохранить в нём исходные требования.
2. Согласовать индивидуальное выполнение практикума.
3. Выбрать технологический стек и средства разработки.
4. Уточнить поля заявки, типы документов, статусы и переходы между ними.
5. Подготовить ER-диаграмму и диаграмму архитектуры.
6. Создать структуру проекта и реализовывать процесс по этапам.
